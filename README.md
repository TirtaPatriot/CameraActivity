# Activity Camera

Open-source camera app for documenting field activities, with a self-hosted server.

- **App** (Android & iOS, Kotlin Multiplatform + Compose Multiplatform): opens straight into the camera. Photos get a watermark the officer arranges (card, strip or minimal; drag to move) with date-time, GPS, task, officer and note. The main action after a shot is **Share** through the system share sheet (WhatsApp, Telegram, e-mail…), with a ready-made caption including a Google Maps link — the way field officers already report to supervisors and groups. Every capture is also uploaded in the background to the organization's server.
- **Server** (Ktor): receives uploads, stores files on disk/NAS and metadata in SQL Server, and hosts an **admin panel** where each organization manages its branding, rules, task types and officer accounts.

One app build serves any organization. Connecting to a server and signing in are optional and only suggested: the camera works without them, uploads can be anonymous (recorded per device) when the admin allows it, and the admin can later require sign-in or a task.

UI languages: **Indonesian (default)** and English, in the app and in the admin panel.

## How it works

```
 Phone (app)                              Server (Ktor, Docker)                Storage
 ───────────                              ─────────────────────                ───────
 Camera (no setup needed) → watermarked photo saved on the phone → Share (system sheet)
 Connect (optional): QR / URL ──GET /api/v1/config──▶ branding, rules, task types
 Sign in (optional)           ──POST /api/v1/auth/login──▶ bearer token
 Background upload            ──POST /api/v1/captures──▶ file  ──────────────▶ NAS / disk (STORAGE_ROOT)
   (WorkManager / iOS)                                  metadata ──────────▶ SQL Server (schema cactivity)
 Shared after upload          ──POST /api/v1/captures/{clientId}/shared──▶ shared_at
 Admin (browser)              ──/admin──▶ captures, officers, tasks, branding, rules, connect QR
```

- Branding (organization name, in-app title per language, primary color, logo), task types and rules are edited in the admin panel and picked up by the app on the next start; the last configuration is cached so the app works offline. Rules start permissive on purpose: anonymous uploads allowed, sign-in and task optional. Tighten them once officers are used to the app (*Require sign-in*, *Require a task*, *Require GPS*, photo/video, audio, max video length, default language).
- Recorded with each capture: device id and model, time taken vs. time uploaded, task, whether the location was reported as **mock** by the OS (allowed but flagged in the panel), and when it was **shared** from the phone.
- The app's home-screen name and icon are fixed at build time; to change those, build your own app with a different name/icon (see *Rebranding the app build*).
- Each capture has a UUID generated on the phone, so re-uploads never create duplicates. The officer code stored with a capture always comes from the signed-in account.

## Running the server

Requirements: Docker (or JDK 17+), SQL Server, and a writable folder for files (a NAS share mounted on the host works well).

1. Create the database objects by running, in order:
   - `server/sql/001_init.sql`
   - `server/sql/002_accounts_settings.sql`
   - `server/sql/003_tasks_anonymous.sql`
   - `server/sql/004_oidc.sql`
2. Configure the environment (see `server/.env.example`):

   | Variable | Meaning |
   |---|---|
   | `STORAGE_ROOT` | Folder for photos/videos and the logo (`/data` in Docker) |
   | `DB_URL`, `DB_USER`, `DB_PASSWORD` | SQL Server JDBC connection |
   | `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Creates the first admin on first start (min. 8 characters); ignored once an admin exists |
   | `PUBLIC_URL` | Optional; address put in the connect QR (otherwise taken from the request / proxy headers) |
   | `TIMEZONE` | Zone for dates in the panel and date filters (default `Asia/Jakarta`) |
   | `MAX_UPLOAD_MB`, `DB_POOL_SIZE`, `PORT` | Optional tuning |

3. Run it:

   ```bash
   docker build -t activity-camera-server .
   docker run -p 8080:8080 --env-file server/.env -v /mnt/nas/activity-camera:/data activity-camera-server
   ```

   or without Docker: `./gradlew :server:buildFatJar && java -jar server/build/libs/activity-camera-server.jar`.

4. Open `https://<your-server>/admin`, sign in with the admin account, then:
   - **Branding**: organization name, titles, color, logo.
   - **Rules**: what officers may capture and what the stamp shows.
   - **Officers**: create an account for each officer.
   - **Connect phone**: shows the QR the app scans.

Put the server behind HTTPS (e.g. Traefik/Dokploy); it honours `X-Forwarded-Proto/Host`. The server refuses to start if the storage folder is not writable, the database is unreachable, or no admin exists and `ADMIN_*` is not set.

### Single sign-on (OpenID Connect)

Officers and admins can sign in through the organization's identity provider — any OpenID Connect provider (Casdoor, Keycloak, Authentik, Google Workspace, Microsoft Entra, …). The server is the OIDC client (authorization code + PKCE, client secret stays on the server); the app opens the system browser (Custom Tabs / ASWebAuthenticationSession, so an existing SSO session is reused) and receives a one-time code bound to the app with PKCE, which it exchanges for the server's own token.

1. At the provider, create an application (confidential client, grant type *authorization code*) with redirect URI `<PUBLIC_URL>/auth/oidc/callback`. For Casdoor: *Applications → Add*, copy the client ID and secret.
2. Set `PUBLIC_URL`, `OIDC_DISCOVERY_URL` (e.g. `https://sso.example.org/.well-known/openid-configuration`), `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`.
3. Optional: `OIDC_USER_CODE_CLAIM` (employee ID / NIP claim, dotted path allowed), `OIDC_ADMIN_GROUP` (+ `OIDC_GROUPS_CLAIM`), `OIDC_BUTTON_LABEL`.

On the first SSO sign-in an account is linked by the provider's `sub`: to an existing panel account with the same employee ID, or a new officer account. Name, employee ID and (with `OIDC_ADMIN_GROUP`) role follow the provider on every sign-in; disabling the account in the panel still blocks it. With SSO on, *Rules → Officers may sign in with a password* can be turned off; admins can always use a password for the panel (emergency access).

## Building the app

- **Android**: `./gradlew :androidApp:installDebug`
- **iOS** (macOS, Xcode 16+): `brew install xcodegen`, then `cd iosApp && xcodegen generate && open iosApp.xcodeproj`, pick a signing team and run on a device (the camera does not work in the Simulator).

### Rebranding the app build

The in-app branding comes from the server. To publish a build with your own home-screen name, icon and identifiers, change:

- Android: `applicationId` in `androidApp/build.gradle.kts`, `app_name` in `androidApp/src/main/res/values*/strings.xml`, launcher icon in `androidApp/src/main/res/drawable/ic_launcher_*.xml` (adaptive icon: foreground, background, monochrome).
- iOS: `PRODUCT_BUNDLE_IDENTIFIER` and `CFBundleDisplayName` in `iosApp/project.yml`, `iosApp/iosApp/*.lproj/InfoPlist.strings`, app icon `iosApp/iosApp/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png` (1024×1024, no transparency).

## API

| Method | Path | Auth | Description |
|---|---|---|---|
| `GET` | `/health` | — | Liveness check |
| `GET` | `/api/v1/config` | — | Branding + capture rules |
| `GET` | `/api/v1/branding/logo?v=<version>` | — | Organization logo |
| `POST` | `/api/v1/auth/login` | — | `{username, password, deviceName}` → `{token, user}` |
| `POST` | `/api/v1/auth/logout` | Bearer | Revokes the token |
| `GET` | `/auth/oidc/start` | — | Starts SSO (panel, or `?client=mobile&state=&code_challenge=&code_challenge_method=S256` for the app) |
| `GET` | `/auth/oidc/callback` | — | Redirect URI registered at the provider |
| `POST` | `/api/v1/auth/oidc/token` | — | `{code, codeVerifier}` → `{token, user}` |
| `GET` | `/api/v1/me` | Bearer | Signed-in account |
| `POST` | `/api/v1/captures` | Bearer, or none when anonymous uploads are allowed | Multipart upload: `metadata` (JSON) + `file` |
| `POST` | `/api/v1/captures/{clientId}/shared` | Same as upload | `{sharedAtEpochMs}` — capture shared after it was uploaded |
| `GET` | `/api/v1/captures?from=&to=&userId=&limit=` | Bearer (admin) | List metadata |
| `GET` | `/api/v1/captures/{id}/file` | Bearer (admin) | Download the original file |

### Device id (matching other in-house apps)

Each capture carries the phone's OS device id: **ANDROID_ID** on Android and **identifierForVendor** on iOS. Android gives every app signed with the **same signing key** the same ANDROID_ID on a phone (per user; it changes after a factory reset), and iOS gives every app from the **same Apple developer team** the same identifierForVendor. Sign this app with the same key/team as your other apps (e.g. attendance) and the ids match, so captures can be joined with their records. With Play App Signing, choose the same app signing key as the other app when enrolling.

## CI

GitHub Actions (`.github/workflows/ci.yml`):

- **server** (Ubuntu): runs on every push to `main`, pull requests, tags and manual runs; builds the server fat JAR (workflow artifact).
- **android** (Ubuntu): runs only on manual runs (Actions → CI → Run workflow) or when a tag is pushed; builds the debug APK, and a signed release APK when these repository secrets exist: `ANDROID_KEYSTORE_BASE64` (the .jks, base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, and optionally `ANDROID_KEY_PASSWORD` (defaults to the keystore password).
- **ios** (macOS): runs only on manual runs or when a tag is pushed; builds the iOS app for the Simulator, unsigned.

To build the apps for a release, push a tag, e.g. `git tag v0.1.0 && git push origin v0.1.0`.

## Security notes

- Passwords are stored as PBKDF2-HMAC-SHA256 hashes; tokens are random and stored only as SHA-256 hashes.
- Disabling an officer or resetting their password signs them out of every device.
- The admin panel uses an HttpOnly, SameSite=Strict cookie (12-hour sessions).
- On the phone, the session token is kept in the app's private storage. Moving it to the Android Keystore / iOS Keychain is a planned improvement.
- There is no login rate limiting yet; put the server behind a proxy that limits requests to `/api/v1/auth/login` and `/admin/login`.

## Not implemented yet

- Burning the watermark into video frames (video metadata is recorded; the watermark applies to photos).
- GPS in the EXIF of iOS photos (Android writes it; both store it in the capture metadata).
- iOS uploads run while the app is open (plus a short grace period when it goes to the background); Android uses WorkManager and also uploads after the app is closed.
- Reverse geocoding (street address) in the watermark; the share caption has a Google Maps link instead.
